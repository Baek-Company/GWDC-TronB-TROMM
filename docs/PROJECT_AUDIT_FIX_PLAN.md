P0은 거래 또는 위험 동의의 안전 경계를 먼저 고쳐야 하는 항목, P1은 다음 기능 검증 전에 수정할 항목, P2는 후속 품질 작업입니다.

### F-01 · P0 · USDD 거절 문장이 동의로 뒤집힘 — 확인

- **위치:** `server/llm/conversation.ts:37-40,180-181`; 관련 적격성 `shared/eligibility.ts:57-59`.
- **재현:** 다른 조건이 채워진 대화에서 `USDD는 허용하지 않아요`, `USDD는 괜찮지 않아요`, `USDD는 동의 못 해요`를 분석합니다. `explicitUsddDecision`의 긍정 정규식이 부정형의 앞부분을 잡아 `acceptsUsddRisk=true`로 반환합니다. NIM 추출 결과가 `false`여도 180~181행에서 덮어씁니다.
- **수정:** 부정·철회 표현을 먼저 의미 단위로 판별하고, 긍정 단어가 부정의 수식 범위 안에 있으면 긍정 처리하지 않습니다. 긍정/부정이 함께 있거나 불명확하면 `null`로 두고 명시적으로 다시 묻습니다. `contextualizePatch`와 최종 덮어쓰기 모두 하나의 결정 함수만 사용하도록 합칩니다. 거절에서 동의로 바뀌는 경우는 별도의 명시적 긍정 답변만 허용합니다.
- **검증/완료:** `tests/conversation.test.ts`에 위 3문장, 명확한 동의, 혼합/애매한 문장, 모의 NIM이 `false`를 반환하는 경우를 넣습니다. 거절은 항상 `false`, 애매함은 확인 질문, `psm_jusdd` 적격성은 `usdd_risk_declined`가 되어야 합니다.

### F-02 · P0 · 서로 다른 요구 조건에 같은 Plan ID 부여 — 확인

- **위치:** `shared/planning.ts:164-165,168-172`; 소비자 `src/features/execution/index.ts:17-38`, `shared/review.ts:104-106`.

- **수정:** 체인/자산, 보유액, 기간, 각 지출·예비액, 위험 선호·USDD 동의, 확인 버전, 상품·시나리오·배분, 견적 ID/버전을 정렬된 canonical 구조로 직렬화하고 안정적인 해시를 ID에 포함합니다. 기존 ID와 저장 기록은 조용히 새 계획에 재결합하지 않습니다. `v2` 형식으로 구분하고 과거 기록은 읽기 전용으로 보존하거나 명시적 재확인 후 이전합니다.
- **검증/완료:** `tests/planning.test.ts`에서 지출일만 다른 위 사례, 종료일·예비액·위험 동의 변경, 동일 입력의 재계산을 검사합니다. 다른 조건은 다른 ID, 같은 조건은 같은 ID여야 합니다. `tests/execution.test.ts`에서 이전 기록이 다른 새 계획에 연결되지 않아야 합니다.

### F-03 · P0 · 0원 비용이 출처·신선도 검사를 건너뜀 — 확인

- **위치:** `shared/planning.ts:116-136`, 특히 125~130행; 관련 `shared/eligibility.ts:41-44`, `shared/sizing.ts:61-69`.
- **재현:** 필수 비용을 모두 `amount='0'`, `estimatedAt=null`, 오래되거나 `synthetic` 출처로 만들면 `amount.isZero()`에서 먼저 `continue`하여 `roundTripCost='0'`, 양수 순익, `eligible` 계획이 나옵니다.
- **수정:** 금액이 0이어도 비용별 `estimatedAt`과 출처 체인·mode·조회 시각·원천 갱신 시각을 검증한 뒤 합산합니다. 0원이라는 사실도 비용 근거가 필요합니다. 공통 `isCurrentLiveSource(source, chain, now, maxAge)`를 만들어 견적·비용·최소액 탐색에 적용합니다. 출처가 없거나 오래됐으면 비용을 미확인으로 처리하여 적격 계획/손익분기 확정을 막습니다. `sourceUpdatedAt=null`의 허용 여부는 직접 RPC와 집계 REST의 특성에 따라 명시하고, 집계 데이터의 원천 시각이 불명확하면 조건부로 둡니다.
- **검증/완료:** `tests/planning.test.ts`에 0원 비용의 `estimatedAt=null`, 오래된 시각, `synthetic`, 다른 체인, 정상 최신 live 경우를 추가합니다. 앞 네 경우는 eligible/확정 순익이 나오지 않아야 합니다. `source.sourceUpdatedAt`이 오래된 견적과 비용도 적격으로 표시되지 않아야 합니다.

### F-04 · P0 · 여러 탭에서 같은 Nile 거래를 이중 서명할 수 있음 — 확인

- **위치:** `src/features/execution/index.ts:8,112-117`, `src/features/execution/withdraw.ts:10,168-177`.
- **원인/영향:** `inProgress`는 탭마다 별도 `Set`입니다. 두 탭이 동시에 기존 기록 없음으로 판단하면 각각 서명·방송할 수 있고, 단일 `localStorage` 키가 서로 다른 txID 중 하나를 덮을 수 있습니다.
- **수정:** 체인·지갑·계획·동작을 묶은 키로 Web Locks API 같은 브라우저 origin 단위 상호 배제를 서명 전체 구간에 적용합니다. 잠금 **획득 후** 저장 기록과 현재 미리보기를 다시 읽고 검증합니다. 잠금 기능이 없는 환경은 원자성을 보장하는 대안이 준비될 때까지 실행 버튼을 잠급니다. txID별 불변 기록을 별도로 보존하여 마지막 저장이 이전 txID를 없애지 않게 합니다.
- **검증/완료:** 두 독립 탭/컨텍스트가 같은 예치 또는 환매를 동시에 시작하는 테스트에서 서명·방송은 한 번만 일어나고 원 txID가 보존되어야 합니다. 잠금 미지원 환경은 실행 거부를 확인합니다.
- **범위 한계:** 브라우저 origin 잠금은 다른 기기·브라우저 프로필까지 조정하지 못합니다. 다중 기기 거래를 지원하려면 서버 측 지속 idempotency와 거래 이력 조정이 추가로 필요합니다.

### F-05 · P1 · 서명 전 오류가 거래 상태를 영구 잠금 — 확인

- **위치:** 예치 `src/features/execution/index.ts:148-149,183-199`; 환매 `src/features/execution/withdraw.ts:206-207,236-253`.

- **검증/완료:** `tests/execution.test.ts`에서 builder 실패, 서명 4001, 서명 비4001, 방송 시간 초과를 두 동작에 각각 시험합니다. 앞의 서명 전 오류는 재시도 가능하고, 방송 불확실성은 새 서명 없이 기존 txID 조회만 가능해야 합니다.

### F-06 · P1 · 오래된 탭의 재조회가 확정 영수증을 되돌림 — 확인

- **위치:** `src/features/execution/index.ts:203-225`, `src/features/execution/withdraw.ts:256-280`.
- **재현:** 탭 A가 `confirmed`를 저장한 뒤, 이전 `pending` 기록을 쥔 탭 B의 늦은 재조회가 `pending`/`unknown`을 같은 키에 저장하면 UI에서 확정 증거가 사라질 수 있습니다.
- **수정:** F-04의 탭 간 잠금 안에서 최신 저장 기록을 같은 `record.id`·txID 기준으로 재조회하고 상태 전이와 저장을 한 구간으로 처리합니다. `confirmed`/`failed` 같은 종결 상태에서 `pending`/`unknown`으로의 회귀를 금지하고, 충돌 시 원본 기록과 증거를 보존합니다. `storage` 이벤트로 다른 탭에 최신 상태를 알립니다. txID별 불변 기록 설계와 함께 구현합니다.
- **검증/완료:** 지연된 pending 응답과 먼저 저장된 confirmed 응답의 interleaving 테스트에서 confirmed와 영수증·실제 수수료가 남아야 합니다. 예치·환매 모두 검사합니다.

### F-07 · P1 · 손상된 세션을 초기 세션으로 자동 덮어씀 — 확인

- **위치:** `src/lib/session.ts:41-48`, `src/main.tsx:82,94`.
- **재현:** `gwdc-lee-mir-session-v1`에 잘린 JSON이나 다른 `schemaVersion`이 있으면 `loadSession()`이 초기 세션을 반환합니다. 첫 effect가 같은 키에 곧바로 저장해 이전 계획·기록 원문을 지웁니다.
- **수정:** 로딩 결과를 `absent | valid | invalid`로 구분합니다. `invalid`이면 원문을 유지하고 백업/내보내기와 복구 안내를 제공하며, 사용자님의 명시적 초기화 또는 성공적 마이그레이션 전에는 같은 키에 쓰지 않습니다. 새 스키마 도입 시 버전별 이행 함수를 둡니다. `saveSession`의 저장 용량 초과/쓰기 거부도 UI 오류로 다루고 현재 메모리 상태의 JSON 내보내기를 제공합니다.
- **검증/완료:** 손상 JSON/구버전 세션 새로고침 뒤 원문이 그대로 있고 복구/내보내기가 가능해야 합니다. 정상 세션 round trip, 빈 저장소 초기화, `setItem` 예외 후 현재 세션 내보내기도 검사합니다.

### F-22 · P2 · 외부 데이터 준비 상태와 제출 기준 — 운영 확인

- **근거:** `./scripts/run run doctor`의 이번 네트워크 허용 실행; `docs/PROJECT_PLAN.md`, `docs/IMPLEMENTATION_STATUS.md:10-17,25-27`.
- **현상:** Mainnet PSM 진입/출구·토큰·용량과 Stake 2.0 RPC는 HTTP 429입니다. 지갑 잔고·Nile 수수료 리소스, SUN 경로 적합성도 일부 미확인입니다. 현재 Mainnet A/B의 실거래 가능 계획 2개와 Nile solidified txID/포지션은 증명되지 않았습니다. 이것은 429 자체를 코드 결함으로 확정한 것이 아닙니다.
- **수정:** 각 외부 원천에 적절한 제한 속도·백오프·요청 묶음/캐시를 적용하되 오래된 캐시를 live로 승격하지 않습니다. PSM은 양방향 실제 출력 토큰·용량·비용·허용량과 주소를 독립 검증하고, Nile은 별도 시험 계정으로 지갑/리소스/solidified 영수증을 확인합니다. `doctor`의 `unavailable`과 `unknown`을 작업 티켓과 제출 증거로 분리해 추적합니다.
- **검증/완료:** 각 출처의 chain, source URL, fetchedAt/sourceUpdatedAt, 주소·단위, 요청/응답 근거를 비밀값 없이 기록합니다. 외부 상태가 해결되지 않으면 해당 계획은 conditional/excluded를 유지합니다.

### F-23 · P3 · 예치 시 현재 `getCash` 게이트의 정책 재검토 — 정책 결정 필요

- **위치:** `server/transactions.ts:279-281`; 별도 출구 판정 `shared/eligibility.ts:48-53`.
- **현상:** `getCash() < 예치액`이면 `mint()` 사전 실행 전 차단합니다. 기존 풀 현금이 예치액보다 작아도 공급 거래 자체는 성공할 수 있으므로 일반적인 mint 필수 조건은 아닙니다. 다만 프로젝트의 보수적인 **즉시 전액 출구 유동성** 정책일 수 있어 확정 버그로 분류하지 않습니다.
- **수정 선택:** 정책을 유지한다면 이 제한이 왜 필요한지 UI/문서·진단에 분명히 표시하고 유동성 부족과 거래 실패를 구분합니다. 정책을 바꾼다면 예치 가능성은 시장 활성·잔고·수수료·`mint()` 시뮬레이션으로 판단하고, 출구 현금은 별도 위험/계획 적격성으로 평가합니다.
- **검증/완료:** 선택한 정책의 `cash=0`, `cash<amount`, `cash≥amount` 시험과 UI 안내가 일치해야 합니다.
- **공식 근거:** [JustLend 공급 개념](https://docs.justlend.org/getting_started/concepts/supply/)과 [SBM 계약 문서](https://docs.justlend.org/developers/supply_and_borrow_market/sbm/)는 `mint()`를 공급 호출, `getCash()`를 시장의 현재 기초자산 보유량으로 설명합니다. 현재 코드의 `getCash ≥ 예치액` 조건을 프로토콜의 일반 mint 필수 조건으로 제시하지 않습니다.

### F-25 · P1 · 잘못된 요청 대상 하나가 로컬 API를 종료시킬 수 있음 — 확인

- **위치:** `server/index.ts:47-54,135-140`.
- **재현/영향:** `new URL(req.url, 'http://localhost')`가 async HTTP 리스너의 `try` 바깥에 있습니다. Node 24에서 `//%5B` 같은 잘못된 request-target은 `ERR_INVALID_URL`을 던지고 처리되지 않은 Promise 거부로 프로세스가 종료될 수 있습니다. 다른 로컬 프로세스는 loopback API에 요청할 수 있습니다. 외부 웹페이지에서 로컬 주소로 GET을 유도하는 경로는 브라우저의 로컬 네트워크 접근 정책에 따라 달라집니다.
- **수정:** URL 생성과 pathname 접근도 요청 처리 `try` 안으로 옮깁니다. 잘못된 target은 400 JSON으로 응답하고, `send` 자체가 안전하게 호출되도록 공통 오류 경계를 구성합니다. 정상 라우트의 기존 4xx/502 구분은 유지합니다.
- **검증/완료:** 별도 테스트 API 프로세스에 원시 `//%5B` 경로를 보낸 뒤 400을 받고, 이어서 `/api/health`가 200으로 계속 응답해야 합니다. 실제 사용 중인 로컬 서버를 종료시키는 재현 시험은 하지 않습니다.

### F-26 · P2 · 무제한 GET이 외부 API·MCP 자원을 반복 소비 — 확인

- **위치:** `server/index.ts:55,114-130`, `server/data/usdd.ts:48-52`, `server/mcp/trongrid.ts:190-194`, `server/mcp/clients.ts:70-86`.
- **원인/영향:** Origin 검사는 POST만 다루며, `GET /api/sources` 한 번에 PSM·Stake·SUN·MCP·TronGrid 조회가 병렬로 시작됩니다. 다른 로컬 프로세스의 반복 GET은 설정된 경우 하위 MCP 프로세스와 제공자 할당량을 소모합니다. 외부 웹페이지의 단순 GET 경로는 브라우저의 로컬 네트워크 접근 정책에 따라 달라집니다. `/api/nile`, 거래 조회, 관측도 외부 호출 제한이 없습니다.
- **수정:** 고비용 GET에 동시 실행 상한·호출 빈도 제한과 짧은 in-flight 공유/결과 캐시를 적용합니다. 다른 웹페이지의 단순 GET을 줄이기 위한 Fetch Metadata 검사도 검토하되, Origin 유무만으로 방어했다고 판단하지 않습니다. `readMarkets(true)` 등의 캐시 우회는 필요한 새로고침 때만 허용합니다. 오래된 캐시는 새로운 live 조회로 가장하지 않고 원래 시각·mode를 보존합니다.
- **검증/완료:** 병렬/반복 요청 부하 테스트에서 상류 API·MCP 호출 횟수가 설정한 상한을 넘지 않고, 제한 시 429 또는 명시적 재시도 안내를 반환합니다. 정상 단건 조회와 새로고침은 계속 동작해야 합니다.
