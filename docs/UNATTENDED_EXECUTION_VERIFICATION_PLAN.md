# 무인 실행 추가 검증 단계 계획

작성일: 2026-09-29 · 상태: **검증 계획, 실행 전**

이 문서는 [잔액 기반 거래 에이전트 구현 계획](AUTONOMOUS_AGENT_PLAN.md)의 각 코드 단계가 끝날 때마다, **무인 거래를 켜도 되는지** 판정하기 위한 실행 절차입니다. [계획 검증 결과](AUTONOMOUS_AGENT_PLAN_VALIDATION.md)의 선결 조건을 구체적인 시험·증거·합격 기준으로 바꿉니다. 이 문서 작성 자체는 지갑 연결, 서명, 거래 방송, 금고 배포 또는 보안 감사의 완료 증거가 아닙니다.

## 0. 현재 코드에서 먼저 닫을 구현 게이트

| 게이트 | 필요한 구현·연결 | 통과 증거 |
| --- | --- | --- |
| 0B→A | 현재 읽기 전용 포트폴리오 관측과 원장/코디네이터를 인증된 TronLink 확인·미리보기·서명·방송 UI에 연결합니다. 브라우저 제공 JSON이나 주소만으로 의도를 승인하지 않습니다. | 서명 전 서버 예약, 같은 계정/체인/미리보기 서명 대조, 원 txID와 암호화된 원문을 방송 전 원장 접수, 재시작·거절·기기 경쟁 모의 시험. |
| A 실증 | 별도 Nile 시험 지갑에 시험 TRX와 수수료 재원을 준비하고 예치·환매의 실제 체인 증거를 확보합니다. | 4절의 A-PASS. 미확정 상태나 임의 화면 캡처는 증거가 아닙니다. |
| A→B-1 | 현재 정책 평가·주기 초안을 실제 별도 Nile 시험 지갑의 관측/스케줄러/실행자에 연결합니다. 지갑 소유 확인·정책 변경 인증·키 접근 제한을 구현합니다. | 중복·중단·만료·장애 시험과 B1-01~04의 원장/체인 증거. 기본 모드는 `observe_only`입니다. |
| B-1→B-2 | 실제 Nile 금고 호환성 PoC 후 자산·계약·함수·수량·기간을 온체인에서 강제하는 금고를 구현하고 독립 검토합니다. | 6절의 B2-PASS와 금고 소유자의 서버 독립 pause/회수 실증. |
| Mainnet | PSM 양방향 실출력·왕복 비용과 jToken 계약/시장 상태를 같은 평가 구간에서 검증하고 단계별 승인/잔여 자산 회수 경로를 구현합니다. | 7절 Mainnet A 각 txID·실수령·비용 증거, 이후 별도 B 심사. |

현재 [구현 상태](IMPLEMENTATION_STATUS.md)에서 첫 행의 인증된 UI 연결과 실제 Nile A 거래부터 아직 통과하지 못했습니다. 이 구현 게이트를 건너뛰고 뒤 절의 시험 결과를 `pass`로 기록하지 않습니다.

## 1. 판정 원칙과 환경

- 검증은 `코드/모의 시험 → Nile 사용자 승인형 A 실증 → Nile 별도 시험 지갑 B-1 → Nile 제한 금고 B-2 → Mainnet 승인형 소액 실증 → Mainnet 무인 활성화 심사` 순서로 진행합니다. 앞 단계가 실패하거나 증거가 없으면 다음 단계의 거래는 열지 않습니다.
- B-1은 **TronLink 원지갑과 분리된 Nile 전용 지갑**에서 실행기·원장·스케줄러를 시험합니다. 서버 정책이 한도를 지킬 뿐, 키 탈취 시 온체인에서 손실을 제한하지 못하므로 사용자 자산 운용의 합격 판정으로 쓰지 않습니다.
- B-2는 **사용자님이 명시적으로 배정한 금고 자산**만 무인 운용합니다. 원지갑의 잔액이나 미래 입금에 대한 자동 서명 권한을 요구하지 않습니다. 금고가 체인에서 거부한 거래를 서버 정책 통과로 덮을 수 없습니다.
- 모든 금액은 토큰 최소 단위의 정수 문자열, 시각은 시간대를 포함한 ISO 시각, 체인은 `nile` 또는 `mainnet`으로 기록합니다. 시험 설정에는 허용 계약/함수, 회당·UTC 일일·누적 한도, 최대 수수료, 만료 시각, 보호 지출과 예비액, 대상 주소를 **실행 전에** 고정합니다. 임의의 기본 실거래 한도는 두지 않습니다.
- `not_run / pass / fail / blocked` 네 상태를 사용합니다. 응답이 없거나 429, 자료가 오래됨, 원 txID/영수증 누락은 `pass`가 아닙니다. 단위 테스트의 모의 영수증, 브라우저 화면의 `submitted`, 거래 방송 성공은 체인 `confirmed`와 구별합니다.
- 최초 설치 상태와 각 단계의 기본 정책은 `observe_only`이며 실행자 키 또는 금고 자산이 준비되어 있어도 검증 전에는 자동 거래를 시작하지 않습니다. 실제 Nile/Mainnet 자산을 쓰는 시험은 테스트 대상·금액·수수료 상한·중단 방법을 별도 실행 기록에 확정한 뒤 진행합니다.

## 2. 필수 증거 묶음

각 시험 케이스에 `caseId`, 코드 커밋/빌드 ID, 체인·네트워크 ID, 지갑/금고 주소, 정책 ID·버전·해시, 입력 JSON 확인 버전, 계획/견적 ID·버전, 사용한 근거의 URL·조회/원천 시각·블록, 의도 ID·`triggerId`, 계약·함수·수량·최대 수수료, 실행 전/후 잔액과 포지션, 서명 주체, **원 txID**, 방송 응답, solidified 영수증/블록/결과, 실제 수수료, 실제 수령액, 재관측 결과, 원장 상태 전이와 시험 시각을 연결합니다. 비밀키·복구 구문·API 키·서명 거래 원문은 증거 번들에 넣지 않습니다. 서명 거래 원문의 보관·삭제는 구현 계획의 접근 제한 정책을 따릅니다.

```json
{
  "caseId": "B1-04",
  "status": "not_run",
  "environment": "nile",
  "commit": null,
  "policyVersion": null,
  "accountOrVault": null,
  "intentId": null,
  "triggerId": null,
  "quoteId": null,
  "quoteSourceBlock": null,
  "txId": null,
  "solidifiedBlock": null,
  "receiptResult": null,
  "actualFeeBaseUnits": null,
  "actualReceivedBaseUnits": null,
  "positionBeforeBaseUnits": null,
  "positionAfterBaseUnits": null,
  "evidenceFiles": [],
  "reviewedBy": null
}
```

위 JSON은 **빈 기록 양식**입니다. 해당 값이 `null`인 실제 시험은 그 근거를 확보했다고 볼 수 없습니다. `confirmed` 합격에는 원 txID와 같은 체인의 solidified `SUCCESS` 영수증, 동일 주소·동일 포지션의 거래 후 관측이 모두 필요합니다. 수익/출금 성공 판정에는 실제 수령액과 실제 수수료가 추가로 필요합니다. 동시 외부 거래로 현금흐름을 귀속할 수 없으면 `unknown`으로 남기고 손익·다음 자동 거래를 보류합니다.

## 3. 공통 코드·장애 시험: 모든 실거래 전

`./scripts/run run check`와 관련 타깃 테스트를 통과시키고, `./scripts/run run doctor`의 외부 원천 상태를 기록합니다. `doctor` 성공만으로 금리·출구·서명·거래를 합격 처리하지 않습니다. 아래 케이스는 모의 RPC/지갑/시계, 별도 프로세스와 두 클라이언트를 사용해 재현합니다.

| ID | 주입/행동 | 합격 조건 | 실패 판정 |
| --- | --- | --- | --- |
| C-01 | Nile/Mainnet, 계정, 토큰 주소·decimals·계약 코드를 바꾸거나 지갑을 잠급니다. | 변경 순간 미리보기·기존 의도가 무효화되고 새 거래 0건입니다. 원래 체인·주소로 되돌려도 새 관측/견적/정책 확인 전에는 실행되지 않습니다. | 다른 체인/계정/토큰으로 서명·방송하거나 기존 의도를 재사용합니다. |
| C-02 | 지출일 앞당김, 예비액 증가, 실잔액 감소, 미확정 예약액·수수료 재원 부족, 0/음수 순이익을 만듭니다. | 서버가 확인 입력·최신 Nile 견적으로 보호액과 배분액을 재계산하며 부족하면 거래 의도 0건입니다. 0/음수·미확인 순이익은 투자 권고·무인 실행을 `hold`로 끝냅니다. Nile A의 명시적 기술 시험 예외는 아래 조건을 따릅니다. | 보호할 자금이나 수수료 재원을 거래하거나 수익 미확인을 투자 권고로 바꿉니다. |

| C-06 | 서버 종료·재시작·DB 잠금/쓰기 실패·시간대 전환·UTC 일일 경계를 재현합니다. | 원장/정책/원 txID를 복원하고 중복 실행하지 않습니다. UTC 하루의 사용량과 주기별 `triggerId`는 재시작 전후 동일합니다. DB가 쓰기 불가면 신규 거래 0건입니다. | 재시작·임대 만료·날짜 경계가 새 거래 허가로 변합니다. |
| C-07 | LLM 문장, 시장 조사 응답, 토큰 메모에 임의 계약·실행 지시를 넣고 읽기/정책 API를 인증 없이 호출합니다. | 외부 텍스트는 설명 데이터로만 남고 allowlist/한도/서명 대상이 바뀌지 않습니다. 정책 변경은 지갑 소유 확인·재생 방지·세션 인증을 요구합니다. | 프롬프트/외부 응답이 거래 도구를 호출하거나 무인 정책을 바꿉니다. |

**공통 게이트:** 위 항목 중 하나라도 `fail`, `blocked`, `not_run`이면 A/B의 실거래 검증을 시작하지 않습니다. 단, 특정 시장만 장애라면 다른 시장의 **읽기 전용 조사**는 계속할 수 있고, 거래 가능 판정은 해당 시장별로 따로 내립니다.

**Nile A 기술 시험 예외의 범위:** 이 단계는 전용 시험 지갑의 테스트 TRX로 1회 예치·별도 승인 환매를 증명하는 실험입니다. 금리·미래 환매 비용·순이익이 미확인 또는 음수여도 투자 권고나 B 무인 거래로 승격하지 않습니다. 서버가 확인된 입력 JSON의 지출·예비액을 보호하고 최신 Nile 견적·실잔액에서 예치액을 재계산해야 합니다. 서명 직전에는 Nile 체인·실제 계정·jTRX 계약 코드·활성 시장·현재 전액 환매에 충분한 시장 현금·금액별 모의 실행·예치 수수료 상한과 지갑 수수료 재원을 다시 확인합니다. 해당 RPC 읽기가 429/타임아웃이거나 값이 불일치하면 시험 거래도 중단합니다. 환매에서는 최신 환율·포지션·시장 현금·환매 모의 실행·수수료 재원을 별도로 확인합니다. 사용자님이 화면의 수량·계약·최대 비용을 확인하고 각 TronLink 거래에 직접 서명해야 합니다. 이 예외는 Mainnet 거래, 수익 추천, B-1/B-2 활성화의 기준을 낮추지 않습니다.

### Nile A 진입 전 C 항목의 모의 검증 현황 (2026-09-30)

아래 `pass / partial / fail / not_run`은 **현재 코드의 Nile 승인형 A 경로에 대한 모의 시험 범위**만 나타냅니다. 1절의 정식 게이트 상태나 체인 거래 성공 상태를 뜻하지 않습니다. Nile A에 적용되는 C-01~07 모의 시험은 통과했고, 이후 별도 TronLink 승인으로 예치·환매의 실제 원 txID·solidified 영수증·동일 포지션 및 실수령을 확인했습니다. 따라서 8절의 **Nile 승인형 A 실증**만 `pass`이며 공통 게이트 전체와 B/Mainnet 경로는 `not_run`입니다. C-02의 수익 권고·무인 한도, C-03의 Mainnet PSM, C-06의 실행자 정책 복구, C-07의 무인 정책 변경 인증은 해당 B/Mainnet 경로 구현 후 다시 시험합니다.

## 4. 선결 실증: Nile 승인형 A

1. 별도 Nile 시험 계정과 실제 TronLink에서 현재 체인·계정·TRX 잔액·수수료 재원·jTRX 계약/기초자산을 확인합니다. 시연의 `1,000 USDT`나 Mainnet 조회값을 Nile 실잔액으로 사용하지 않습니다.
2. 사용자 승인형 소액 예치를 **한 건만** 수행합니다. 서버 예약 의도와 브라우저 서명 거래의 계정·체인·대상·함수·수량·수수료 상한·만료가 일치하는지, 원 txID를 방송 전에 원장에 접수했는지 기록합니다. 거절/잠금/계정 전환 시 서명과 방송이 없는지 별도 시험합니다.
3. 원 txID의 solidified 영수증에서 성공/실제 수수료를 확인하고 같은 계정·jTRX 포지션의 예치 전후 수량을 대조합니다. 이어서 **별도 TronLink 승인**으로 소액 환매하고 동일한 검증을 반복합니다. 환매 TRX 실수령은 해당 거래 이벤트와 잔액·포지션 변화로 귀속합니다. 다른 거래가 겹치면 실수령 미확인으로 처리합니다.
4. `A-PASS`는 예치와 환매 각각의 원 txID·solidified 성공 영수증·실제 수수료·같은 포지션 변화가 연결되고, 환매 실수령량과 초기 투입량을 실제 현금흐름으로 정리했을 때만 부여합니다. 영수증이 pending/unknown이면 기다리거나 원 txID만 재조회합니다. 실제 순수익 계산이 불가능하면 B에서 그 값을 정책 근거로 쓰지 않습니다.

## 6. B-2: Nile 제한 금고 검증

1. **호환성 PoC:** 실제 Nile 금고 주소에서 jTRX `mint`·`redeem`을 소액 호출합니다. 포지션 토큰이 금고에 귀속되고 환매 TRX가 금고로 돌아오는 것을 같은 체인 영수증/잔액으로 확인합니다. 지갑 직접 호출의 성공, ABI나 배포 주소 대조만으로 금고 호환성을 통과시키지 않습니다. PoC 실패 시 금고 설계를 수정하고 이 단계는 `blocked`입니다.
2. **온체인 거절:** 허용 외 실행자, 잘못된 계약·함수, 다른 수령 주소, 만료된 정책, 회당/UTC 일일/누적 신규 예치 원금 한도 및 현재 포지션 노출 상한 초과, 최소 실수령액 미달, 재진입/실패 반환값을 각기 호출합니다. 모든 위반 거래가 체인에서 거절되고 금고 자산·사용 한도가 성공 거래 외에는 변하지 않아야 합니다. 환매로 현재 노출이 줄어도 소진된 일일·누적 예치 한도는 복원되지 않아야 합니다.
3. **운영 중단:** 백엔드와 실행자를 중지한 상태에서 소유자 TronLink로 pause·권한 철회·금고에 남은 원자산/포지션 토큰의 긴급 회수를 시험합니다. 이미 방송한 tx는 취소된 것처럼 표시하지 않습니다. 시장 유동성이 없으면 기초자산 즉시 환매는 보장하지 않으며, 회수 가능한 자산의 종류와 양을 정확히 보여야 합니다.
4. **독립 검토:** 금고 계약 코드·배포 바이트코드·초기 정책·관리자/업그레이드 권한·키 보관을 구현자와 분리된 검토자가 확인합니다. 발견 사항의 수정과 재시험을 기록합니다. 자가 테스트만으로 이 항목을 `pass`로 표시하지 않습니다.

**B2-PASS**는 호환성 실거래, 거절 매트릭스, 독립 중단/회수, 독립 보안 검토가 모두 통과하고 금고의 배정 자산만 제한된다는 사실이 영수증/잔액으로 보일 때 부여합니다. 하나라도 미실행이면 Nile 금고를 `observe_only`로 유지합니다.

## 7. Mainnet 출시 게이트

1. **읽기·시세:** 같은 평가 구간의 블록/시각에서 jUSDT/jUSDD 계약 코드·`underlying()`·활성 상태와 USDT↔USDD PSM 양방향 토큰 경로, 실제 수량별 출력·용량·최소 수령액·승인·왕복 비용, Energy/Bandwidth·수수료 재원을 검증합니다. REST 원천 갱신 시각이 없거나 RPC 불일치/429가 나면 해당 후보는 `insufficient_data`입니다. 두 경로가 확인되지 않으면 프로젝트의 두 경로 비교를 달성한 것으로 표시하지 않습니다.
2. **Mainnet A 소액:** 각 단계의 별도 TronLink 승인을 전제로 `USDT approve → jUSDT mint → jUSDT redeem`, 검증된 경우에만 `PSM 진입 → USDD approve → jUSDD mint → jUSDD redeem → PSM 출구`를 **각각 별도 txID**로 기록합니다. 매 단계 뒤 잔액·allowance·실제 수령량을 대조하고 실패 시 다음 단계를 멈춘 뒤 잔여 자산/승인액을 표시해 사용자 승인형 회수 절차를 시험합니다. Nile 실증으로 이 단계를 대신하지 않습니다.
3. **Mainnet B 심사:** A의 전 구간 실증, B2-PASS, 독립 금고 보안 검토, 키/서버 운영·감시·사고 복구 점검, 소액 배정/중단/회수 실증이 모두 통과한 경우에만 특정 금고·체인·자산·계약·함수·한도·만료에 대한 활성화 여부를 별도 판정합니다. 자료가 없는 경로는 비활성화합니다. 활성화 뒤에도 첫 실패·데이터 만료·원장 장애·한도 초과·미확정 원 txID는 신규 거래를 자동 중단합니다.
